# Earlier technical plan (superseded)

The current, reconciled plan is [docs/FEASIBILITY.md](docs/FEASIBILITY.md). This earlier draft is retained for historical context. Decisions made after this draft include local saved ideas, three ideas per generation, and a redesigned interview.

Status: draft for product decisions, 26 September 2026.

## Product premise

A playful terminal inspired idea generator for builders, hackathon teams, and hobbyists. A short, personality based interview produces a surprising project concept with enough structure to start building. Users can refine, reroll, accept, and save ideas without an account.

**Working assumption:** “bad idea” means intentionally odd or funny, yet buildable. The product should never present a purely unusable joke as its main result. This needs a product decision before prompt tuning.

## MVP user journey

1. Landing screen opens directly into the terminal window. The header contains the character icon/name, connection status, and theme control. A short welcome shows three obvious actions: **Generate an idea**, **View saved ideas**, and **Help**.
2. `/generate` starts a fixed interview of 4–6 questions. Every question offers tap friendly options and an optional free text answer. Recommended questions: domain; build time/team size; technical comfort; desired tone on a silly-to-practical scale; one interest, annoyance, or constraint. Offer **Surprise me** and **Skip** where useful.
3. Before generation, show a compact summary that can be edited. Generate 2 ideas initially, each as its own structured card. Show a visible loading state and a cancel/retry path.
4. Each card offers **Save**, **Refine**, **Reroll**, and **Copy**. Refinement takes a specific instruction (for example, “make it a weekend project”) and creates a new version while preserving the original.
5. `/saved` opens a saved-ideas view in the same shell. Accountless saves persist on the current device. Export or copy a saved idea as Markdown/JSON; explain that clearing browser data removes local saves.
6. `/help` shows the available commands. Slash commands are shortcuts; users can complete the entire flow without typing them.

## Interaction and visual direction

- Use a **terminal frame**, not a terminal emulator. The macOS style red/yellow/green dots are decorative (unless real actions are assigned); do not mimic a real shell prompt with fake permissions or errors.
- The title bar carries the character identity, for example `musebot · idea lab`. The icon is an inline SVG with a few states: idle, thinking, speaking, and error. Subtle bounce/blink is enough; respect reduced-motion settings.
- Use a single scrollable transcript. Bot messages, user selections, system notices, question controls, and idea cards are typed components with distinct visual treatment. Keep input and the current question anchored near the bottom.
- On mobile, use the full viewport width, comfortable touch targets, a composer that stays clear of the keyboard and safe area, horizontally wrapping option chips, and no horizontal scrolling in idea cards. On desktop, constrain the transcript to a readable width within the terminal frame.
- Color is driven by semantic tokens: background, surface, text, muted text, border, primary, accent, and focus. Define complete theme palettes (dark neutral, magenta, indigo, blue, pastel green); do not derive all contrast colors from only three user chosen hues. Persist the theme locally.
- Animate *already received* bot text in short chunks, with a skip animation control. Keep idea cards instant or reveal them by section; avoid a slow character by character animation for long text. Display an immediate thinking state while waiting for the model.
- Use a readable mono font for short terminal cues and a complementary UI font for longer card text. Ensure keyboard focus, screen reader labels, contrast, and reduced-motion behavior are part of the initial implementation.

## State model and data contract

The title bar character is presentation metadata, so it does **not** require a backend table. Store its name, icon, voice rules, and visual states in frontend configuration. Only persist a `characterId` if multiple characters later affect generation.

For the MVP, model the interview and transcript in the client. The generation request sends **normalized answers**, not a replay of the whole visible transcript. Keep prompt instructions on the server.

```ts
type Answers = {
  domain: string;
  buildTime: 'hours' | 'weekend' | 'week';
  teamSize: 'solo' | 'small-team';
  skillLevel: 'beginner' | 'intermediate' | 'advanced';
  silliness: 1 | 2 | 3 | 4 | 5;
  interest?: string;
  constraints?: string;
};

type Idea = {
  id: string;                  // generated by our app
  title: string;
  oneLiner: string;
  hook: string;                // surprising/funny twist
  audience: string;
  problem: string;
  solution: string;
  mvpFeatures: string[];       // 3–5 concrete items
  suggestedStack: string[];
  firstSteps: string[];        // 2–4 build actions
  scope: 'hours' | 'weekend' | 'week';
  caveat: string;              // biggest feasibility constraint
  parentIdeaId?: string;       // lineage after refinement
  createdAt: string;
};
```

The model returns the content fields. The server validates them, adds IDs and timestamps, and returns `Idea[]`. Keep a schema version with saved records so the local store can migrate if the card shape changes. Transcript items can be a discriminated union (`bot`, `user`, `question`, `idea`, `status`) rendered by one component per type. The transcript is ephemeral in v1; only saved ideas, draft answers, and theme need local persistence.

## Architecture

**Recommended MVP:** Next.js App Router + React + TypeScript, with a server Route Handler for `POST /api/ideas` and `POST /api/ideas/refine`. This runs on Node.js and avoids maintaining a separate backend service for two endpoints. Keep model access behind a small provider interface so it can change later. Next.js Route Handlers are designed for custom request handlers inside `app/api` ([docs](https://nextjs.org/docs/app/getting-started/route-handlers)).

**UI:** Tailwind CSS for tokens/utilities plus a few headless accessible primitives (Radix or selected shadcn/ui components) for menus, dialogs, and tooltips. Most of the terminal, transcript, and idea card should be custom components. Tailwind is a styling tool, not the design system; the theme tokens, type scale, spacing, states, and component rules form the design system. This project does not need a broad component library.

**Storage:** Browser IndexedDB or localStorage for a small accountless collection; choose localStorage first if records stay small, with a storage adapter so IndexedDB can replace it later. No database or account is required for v1. A future sync feature would add anonymous IDs and a database only after defining recovery, abuse, and privacy rules.

**Deployment:** Vercel is convenient for this stack, but not required. Any host that runs the Next.js server and exposes environment variables works. Keep the model API key server side. A static-only deployment would require a separate API service.

**API controls:** Validate request size and values; cap model output and request duration; handle invalid structured output and provider errors; rate limit the public endpoint by a privacy conscious identifier/IP policy; add cost and error monitoring. Never call the model directly from browser code or trust an unvalidated card response.

## AI design

- Deterministic code owns `/help`, `/generate`, `/saved`, question order, answer validation, and UI copy. The model only generates and refines ideas.
- Send a compact structured input and a fixed server prompt defining the character voice, requested silliness, audience, scope, and output rules. Ask for novelty plus a feasible MVP. Treat user free text as data, not new system instructions.
- Use a strict JSON schema for the idea content and validate it again on the server. OpenAI's Structured Outputs supports schema constrained responses ([docs](https://developers.openai.com/api/docs/guides/structured-outputs)). Store prompt version and model name in server logs, without unnecessary personal data.
- Initial managed model candidate: **GPT-6 Luna** with the Responses API. Official OpenAI documentation lists it as an efficient high-volume model and supports structured outputs ([model page](https://developers.openai.com/api/docs/models/gpt-6-luna); [text API guidance](https://developers.openai.com/api/docs/guides/text)). Its actual humor and feasibility need a small side-by-side evaluation before committing.
- Open-weight comparison candidate: **Qwen3-4B**. Its official model card offers an Apache 2.0 licensed download and self-hosted serving options ([model card](https://huggingface.co/Qwen/Qwen3-4B)). Self hosting adds inference operations and may be slower or less reliable for structured output; compare generated cards, latency, and total hosting cost with the same 20–30 interview inputs. “Open source model” should be treated as a license and deployment decision, not a guarantee of zero cost.
- Build a small evaluation set covering funny/serious settings, beginners/advanced builders, healthcare constraints, vague inputs, and adversarial free text. Score novelty, clarity, feasibility, schema validity, and tone. Iterate on the prompt using that set.

## Performance approach

The expected transcript is short, so render it normally. No offscreen card cache or list virtualization is needed for v1. Memoize expensive components only if profiling reveals a problem. Keep saved ideas outside the active transcript when not visible. Optimize the actual bottlenecks first: model wait time, payload size, font loading, image/SVG weight, and mobile keyboard/scroll behavior.

## Build order and exit criteria

1. **Interaction prototype:** responsive terminal shell, theme tokens, character states, deterministic question flow, fake idea data. Test the complete flow at narrow mobile and desktop widths. Exit when it works by touch and keyboard.
2. **Generation:** API route, schema validation, model adapter, loading/error/retry states, 2 idea cards. Exit when the evaluation set gives useful ideas reliably and invalid responses never break the UI.
3. **Refinement and saves:** versioned local storage, save/unsave, refine, reroll, copy/export, `/saved`. Exit when a refresh preserves saves and refinement lineage is clear.
4. **Launch polish:** accessibility pass, performance pass on a midrange mobile device, rate limiting, observability, privacy copy, deployment. Exit when failures are recoverable and model keys remain server side.
